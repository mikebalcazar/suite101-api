asunto: el dominio propio manda de http a https en las siete apps

Mike, 30-sep, con captura: en un Android nuevo abrió quell101.taller101.com
y al picar «Entrar con Google» le salió
{"ok":false,"error":"origen_no_permitido","detalle":{"volver_a":"http://quell101.taller101.com/"}}.

Causa: llegó por http:// (sin la «s»; el navegador lo marcaba con el
triángulo). La app arma `volver_a` con location.origin, y la API sólo
deja volver a orígenes https, con razón. Cloudflare sirve el dominio
propio por http tal cual si la zona no tiene «Always Use HTTPS», y no lo
tiene: los Workers recibían la petición http y contestaban la pantalla.

Arreglo: en `aDominioPropio` de los siete Workers (quell101 #89,
master101 #30, peek101 #20, roster101 #32, quote101 #70, dash101 y
supply101 #100), una lectura (GET o HEAD) por http al dominio propio
contesta 301 a la misma ruta por https, antes de todo lo demás. Un POST
por http no se toca (un 301 lo volvería GET a escondidas); sin
DOMINIO_PROPIO (staging, otras empresas) nada cambia. Cada repo mide el
caso en su prueba de dominio. Verificado desde afuera con curl: los
siete contestan 301 a https.

Lo que NO se hizo: prender «Always Use HTTPS» en la zona de Cloudflare
sería el arreglo de raíz para cualquier subdominio futuro, pero es
configuración de infraestructura viva y la decide Mike; el chat no la
toca. Con el 301 en los Workers ya no hace falta para las apps que hay.
Tampoco se aflojó `volverAPermitido`: seguir exigiendo https ahí es lo
correcto.
